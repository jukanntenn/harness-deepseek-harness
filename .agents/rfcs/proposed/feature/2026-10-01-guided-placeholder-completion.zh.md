# RFC: 用引导式占位符补全被移植技能中的命令

Status: proposed

[English](2026-10-01-guided-placeholder-completion.md) | 中文

## 问题

被移植的技能把 hdsh 的具体工具链事实当作消费方的事实来陈述：pytest 调用与 tests/ 镜像布局、类型面用 basedpyright、未暂存文件的 ruff、本地全集的构成，甚至有一个技能直接点名 hdsh 自己的测试文件路径。对 Rust 或 Node 消费方这些全是死命令，而它们所代表的知识——行为改动跑什么、类型面跑什么、风格跑什么——恰恰是每个仓库必须自己回答的问题。没有任何门禁看得见错误命令，也没有任何东西要求消费方替换它们。实测面是集中于 pushing 与 archiving-rfcs 两个技能的十处命令提及，reviewing 另有嫌疑。

## 提案

本 RFC 是[可迁移语料四分法](../architecture/2026-10-01-transplantable-corpus.zh.md)中"每个仓库各有一个值"一行在技能上的落地。

- **带命令的技能转为模板。** 每个每仓库命令事实变成一个引导式 `TODO(adopt):` 占位符，其文案告诉填写的 agent 要陈述什么，并以 hdsh 的值作为成例——与模板化 standing docs 已在使用的标记相同。
- **占位符检查变成 always-run prek 钩子。** adopt verify 现有的占位符检查接到 prek 的执行点上，于是携带未填槽位的提交会被挡下，诊断里就是填写说明——与推动 standing docs 补全的是同一个 forcing function，移到了提交路径上。
- **槽位在 re-apply 间持久。** 每个占位符位点是上游持有文件中的消费方所有区域：re-apply 重渲染周边文本并保留已填槽值，仅当上游槽位本身变化时报 drift。adopt 托管 prek 块是仓库内"带所有权标记区域"的现成先例。
- **模板直接说消费方形态。** hdsh 命令在模板里写裸形态；调用映射只作用于镜像，模板生来为消费方而写，无需映射。
- **实施前先审计。** pushing 与 archiving-rfcs 已知受影响，reviewing 存疑；审计逐项列出技能集中所有仓库特化事实，只有被审计到的文件转为模板——其余保持逐字节镜像。

## 备选方案

**泛化措辞并链接仓库自己的命令清单。** 否决：指针不是值，清单被跟随时可能未填或缺席，而 hdsh 自己的技能失去具体命令——这正是催生本 RFC 所实现的那一行四分法的缺陷。

**adopt 时机械改写命令。** 与其说否决不如说不可能：消费方的命令在接入时未知，没有可以改写进去的目标；只有消费方能陈述它们。

**填完后让整个技能变为可编辑。** 否决：这会把操作性语料冻结在接入时点，上游的技能修订从此再也无法到达已接入的仓库。

## 验收标准

- 全新接入在填完每个命令槽位之前无法越过占位符钩子提交，且诊断自带填写说明。
- 换新 ref 的 re-apply 保留已填槽值并更新周边文本。
- 上游修改槽位本身时报 drift 并点名重填动作。
- 审计列出每个模板化技能及其槽位数量，未被审计的技能保持逐字节镜像。

## 风险

- 受影响技能存在两份——hdsh 活文件与模板——由逐位点同步门禁维系一致；这是"每仓库一个值"一类已接受的成本，且被限制在被审计文件内。
- 占位符钩子设计上就是提交摩擦；缓解就是诊断本身，因为诊断即说明。
- 槽位持久化是新增机制；以标记区域为界并沿用托管块先例，把它的面收得很小。
