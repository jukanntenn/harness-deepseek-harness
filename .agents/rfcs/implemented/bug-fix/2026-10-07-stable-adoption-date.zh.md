# RFC: 接入日期属于接入本身，而不属于某次运行

Status: implemented

[English](2026-10-07-stable-adoption-date.md) | 中文

## 问题

adopt-RFC 锚点在每次 `hdsh adopt apply` 时都从墙钟重新派生——用的是所配置 Project 时区的日历。第五个接入方跨零点重跑 apply（2026-10-05→10-06，Asia/Shanghai），在第一份三元组旁边得到了第二份完整的带日期三元组：原有的 `2026-10-05-adopting-the-hdsh-harness.md` 及其配对脱离 manifest 的摘要钉定、以孤儿状态滞留，而所有移植语料链接都改指新锚点。manifest 里没有任何东西记录「这次接入已经有日期了」。

## 决策

- adopt manifest 记录 `adoptDate`——按 Project 时区派生的 `yyyy-mm-dd` 字符串，载入即校验；只在早于该字段的 manifest 里为空。
- 只要记录存在，apply 就复用该日期：RFC 锚点、`installed_destinations` 与所有渲染模板都派生自这一个日期，且运行打印一条点名复用日期的注记，让稳定性可见而非靠推断。
- 无该字段的 manifest——早于本变更的接入——从 Project 时区派生一次日期并记录，其后的每次 apply 复用之。
- 接入手册以两种语言写明「只定一次日期」。

## 考虑过的替代方案

**锚点变化时删除旧三元组。** 否决：重跑 apply 不应销毁决策记录，复用让孤儿问题无从产生，而不是用清理去回答它。

**按内容而非日期派生锚点。** 否决：日期前缀是 RFC 树的排序约定——文件名携带首次提出的日期——为一条记录另立命名方案会分裂语料的机械规则。

**记录完整锚点路径而非日期。** 否决：锚点是日期的纯函数；存日期让 manifest 保持最小并可平凡校验，存路径则邀请记录与派生目标之间的漂移。

## 后果

换来的是：重跑 apply 日期稳定——单一三元组、不再移动的语料链接、跨零点重跑后没有孤儿记录；复用注记让该行为在运行输出里可观察。

付出的是：多一个受校验的 manifest 字段（畸形的 `adoptDate` 载入即显性失败），以及在无字段 manifest 下的首次重跑会从当前时钟派生——即变更前的行为，每次旧接入恰好经历一次。

## 验证

manifest 装载测试钉住该字段——缺省为空、非字符串以字段名显性失败、round trip 保留。apply 测试钉住复用——注入的次日时钟把 apply 重放到记录日期上、打印复用注记、不写第二个锚点——以及迁移——无字段 manifest 被记入派生日期，且与磁盘上的锚点一致。
