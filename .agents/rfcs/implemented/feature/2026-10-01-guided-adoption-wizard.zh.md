# RFC: 推导接入参数并为 git 外设置设门禁

Status: implemented

[English](2026-10-01-guided-adoption-wizard.md) | 中文

## 问题

`hdsh adopt plan` 要求六个旗标，其对应事实消费方大多无法从命令行得知，且接入手册的 Phase 2 是工具看不见的人工清单；被扩展的已发布设计见 [adopt RFC](../feature/2026-09-17-hdsh-adopt-and-templates.zh.md)。失败来得晚、落点最糟：错的 Project 编号在仓库第一个 issue 事件上爆炸，账户类型不匹配在每次 workflow 运行里失败，缺失的 gh 或其 stack 能力要等到镜像技能硬停那一刻才被发现，而标签分类、看板形状、机密这些没有任何地方校验。首次接入方需要一场调试会话才能发现工具本可以检查的东西：参数可推导、GitHub 状态可查询、gh 与 hdsh 本身可探测。

## 决策

### 参数解析

- `--hdsh-ref` 默认取上游最新正式版 tag（`git ls-remote --tags` 按 `vX.Y.Z` 过滤、取最高），不存在则响亮失败——上游发布纪律是声明过的前提，且刻意不做 main-HEAD 兜底。撰写本文时上游仓库仍无 tag，因此每个早期消费方都显式传旗标；默认值随第一个 tag 的发布而激活。
- `--account-type` 经 `gh api repos/{owner}/{repository}` 从 origin remote 的 owner 类型推导；非 github.com 的 origin 仍是 blocker。
- `--lifecycle-actor` 从已认证的 gh 身份推导——将要写 Project 变更的凭据正是生命周期用以比对的身份。
- `--time-zone` 默认取从 `/etc/localtime` 链接读出的操作者本地系统时区；GitHub 没有可读取的账户时区。
- 每个推导都在 plan 输出中回显，每个旗标仍是显式覆盖，全旗标运行保持离线——封闭的 e2e 测试套件依赖这一点，且有测试钉住。被阻塞项拒绝的运行把阻塞之前收集到的回显置于阻塞诊断之前打印，参数解析从不藏在中止它的拒绝背后。
- 既有 `config.json` 仍按[配置所有权 RFC](2026-10-01-consumer-configuration-ownership.zh.md) 的定义作为绑定输入；缺省的旗标不再与它冲突——只有显式传入且与文件值矛盾的旗标才是 blocker。
- `--project-number` 与 `--project-title` 保持手输：看板身份是唯有消费方（或未来的建板步骤）才能陈述的东西。

### 绑定锚点

- apply 把解析出的 Project 编号记入 adopt manifest 的 `projectAnchor`——看板绑定。
- verify 将 `config.json` 的 `projectNumber` 与锚点比对：不匹配意味着消费方换了板，诊断指名显式的重绑定动作——以新编号重跑 apply。锚点绝不静默更新；看板改名保持自由，因为编号是地址而非标题。
- node-id 身份守卫与网络侧的绑定/形状校验流程仍是待议工作：它们需要实时 GitHub 状态，而离线的锚点冲突检查已覆盖首批接入方实际撞上的配置错误类别。

### 预检与安装正典

- `hdsh adopt preflight` 运行本地工具链层——git 可运行、gh 已认证、PATH 上有裸 hdsh——每个失败一条诊断、各自点名安装步骤。
- 安装正典是主机安装的 hdsh（PyPI 发布前用 `uv tool install`）；接入手册 Phase 4 已据此重写，Phase 1 现以主机安装步骤与 preflight 检查开篇。
- 凭据、标签创建与看板形状校验仍是 Phase 2 的人工清单：它们是平台强制的所有者同意步骤，向导不能也不应将其自动化抹掉，其程序化验证与 node-id 守卫同属未来的绑定步骤。

## 验证

聚焦测试通过可注入的 transport 逐项钉住解析：旗标永远胜出；最新正式版 tag 是 ref 默认值，无 tag 的上游响亮失败且无 main 兜底；owner 类型映射到 flavor，不可读的 owner 响亮失败；gh 身份推导 actor，未认证的 gh 响亮失败；本地时区链接到 IANA 名，无法链接的时区失败；preflight 对每个缺失工具各报一条诊断，就绪时零输出。集成测试钉住 plan 输出中的回显、全旗标的离线运行、apply 记录的锚点、指名重绑定动作的换板冲突，以及非看板编辑不引发冲突。真实环境探针确认了响亮失败路径：无 tag 的上游与未认证的 gh 各自产生被点名的 blocker。

## 备选方案

**为 ref 做交互式倾向采集。** 否决：接入由 agent 执行，plan 输出就是采集面——agent 读到解析出的默认值，不同意就覆盖，然后重跑。

**无正式版 tag 时回退 main HEAD。** 否决：这会让所有早期消费方常态化运行在未发布门禁上，把上游的纪律失败静默转成消费方风险，且同一天两次接入不可复现。响亮失败是诚实的信号，也更便宜。

**用标题相等性防拿错看板。** 否决：看板标题设计上就允许消费方修改，该守卫会把每次改名变成流水线故障；编号才是地址，锚点携带编号。

**凭据全自动。** 平台的设计使之为不可能——PAT 创建与 App 注册要求所有者同意——所以自动化属于可能之处：preflight 探测与手册 Phase 2 的排序。

## 后果

本变更买到的东西：拥有 gh 与主机安装 hdsh 的消费方只需输入两个参数而非六个；每个推导出的默认值在落地前可见于 plan；错误的看板编号在 verify 即被点名重绑定动作拦下，而不是在第一个 issue 事件上浮现；preflight 点名的工具链缺口正是过去以工作流中途硬停浮现的那些缺口；手册终于写明它期望的安装正典。

本变更的代价：adopt 多了一条依赖网络的路径，由旗标优先的解析顺序与全旗标运行的离线保证所约束——两种执行模式都要测；锚点只存编号，同号换板（删除重建）对离线检查不可见，等待 node-id 守卫；凭据、标签与看板形状校验仍是人工清单项，其自动化是被显式推迟而非静默放弃。
